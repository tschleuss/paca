# OrbStack gateway health-probe child reaping

The local gateway repeatedly became unhealthy at 252 Docker-accounted tasks
under its 256-task limit. Health logs reported `OCI runtime exec failed ...
procReady not received`. Caddy itself kept serving requests; CPU and memory
were low, and local certificate renewal had succeeded.

`docker top` showed only Caddy because it omitted dead processes. A separate,
unprivileged diagnostic container sharing only the gateway's PID namespace found
**246 zombie `ssl_client` children**, all adopted by PID 1 (`caddy`). Raw logs
are retained privately outside Git; no user data or credentials are published here.

## Cause and correction

The configured `wget --no-check-certificate --spider https://localhost/api/healthz`
probe starts BusyBox's `ssl_client` helper. An orphaned helper exits without
being reaped by Caddy. Repeated successful health checks consume task slots until
new exec processes cannot start. This matches the existing
[Caddy Docker issue #276](https://github.com/caddyserver/caddy-docker/issues/276).

Add `init: true` to the OrbStack gateway service. Docker documents that the
[init process forwards signals and reaps children](https://docs.docker.com/reference/compose-file/services/#init).
Keep the pinned image, HTTPS health command, 256-task limit, capabilities and
network guard unchanged. This is a custom-deployment fix, not a change to Paca's
application code or a reason to permit internet access.

## Reproduction

`reproduction.json` was generated by `test_gateway_healthcheck.py` using the exact
configured gateway image and health command. Disposable containers use a synthetic
local TLS responder and a 64-task limit to reach failure quickly. No ports,
production data/CA, credentials or application services are used.

| Case | Successful probes | Result |
|---|---:|---|
| No init, `network=none` | 53 | 54 zombies; next exec fails with `procReady not received` |
| No init, ordinary bridge | 53 | Same failure and zombie count |
| Configured init, `network=none` | 300 | Zero zombies; all probes succeed |

The network-none case has no external connectivity at all. The bridge control
uses only localhost requests/internal certificates but has an ordinary network.
Both fail without init, proving the firewall is not required to cause the defect.
An initial run before the fix also failed its configured-container assertion.

After the correction, six existing lifecycle/backup fixture tests passed. The
reproduction's finally block removes all containers created by that run.

## Local deployment verification

The installed runtime configuration was compared byte-for-byte with the reviewed
source, permitting only the gateway init addition. The existing lifecycle lock
was acquired before replacing the config and recreating **only** the gateway.
Other container IDs were checked unchanged, so the database, object storage and
network keeper were not restarted/replaced. The old config was saved privately.

Live HTTPS, process-table, agent access and outbound-policy results are recorded
in `live-verification.json`. Synthetic probe stress and live checks are separate
evidence; neither claims a long-duration production soak test.
